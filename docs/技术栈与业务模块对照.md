# 移动端技术栈与业务模块对照

更新日期：2026-09-09。用于开发复盘和学习，依据当前 B01 代码及已有业务方案整理。

**当前只有基础 UI、路由和开发用网络检查已实现。下文业务技术选型属于后续规划，不代表业务已经完成。** 全功能范围见 [移动端需求文档](移动端需求文档.md)，重难点分析见 [业务方案](Android业务重难点与全功能展示方案.md)。

## 1. 已使用的基础技术

| 技术 | 对应模块 | 作用与学习重点 |
| --- | --- | --- |
| Kotlin + Jetpack Compose + Material 3 | 首页、业务、助手、任务、我的基础页面 | 用状态驱动 UI；学习组件、布局、浅色/深色主题。业务入口当前为占位 |
| Navigation Compose | 五个一级入口、连接检查子页面 | 管理页面跳转、返回栈，避免重复打开同一入口 |
| ViewModel + Coroutines + StateFlow | 连接检查页面 | 分离界面和请求逻辑，管理加载、成功、失败状态；生命周期感知地收集状态 |
| Retrofit + Kotlin Serialization | 开发用 GET /health | 定义接口、解析 JSON 为 Kotlin 数据类；后续业务 API 沿用此层 |
| OkHttp | 共用网络客户端 | 实际执行 HTTP 请求，统一连接池、超时等配置；Cookie 登录尚未接入 |
| Gradle Kotlin DSL + 版本目录 + Compose BOM | 工程构建、依赖管理 | 集中管理版本，保持 Compose 依赖组合一致；当前为单 app 模块 |
| JUnit + MockWebServer、Compose UI Test、Android Lint | 网络、路由和静态检查 | 分别验证接口行为、页面导航、Android 代码及资源问题 |
| JDK 17 + Android SDK + ADB + 官方模拟器/KVM | 本地开发环境 | 编译、安装、运行和设备调试；当前设备验证为 Android 11 / API 30 |

主要版本：Kotlin 2.2.20、Retrofit 3.0.0、OkHttp 4.12.0、Gradle 8.13；完整配置以 [版本目录](../gradle/libs.versions.toml) 和工程文件为准。

## 2. 后续业务模块与技术对应

以下均为**移动端待实现方案**，按业务归类，不重复列出每个子功能。服务端优先复用现有能力，缺失部分在对应批次核对和补齐。

| 业务模块 | 拟采用的技术 | 解决的具体问题 |
| --- | --- | --- |
| 登录、验证码、账号与权限 | Retrofit、OkHttp CookieJar、Compose；后端 Cookie 会话与权限校验 | 适配现有登录机制；菜单、按钮及数据访问按权限控制，最终由后端校验 |
| 首页概览、指标、现金流日历、公告 | Compose 卡片/列表；复杂图表用本地 Apache ECharts + AndroidX WebKit | 手机上清晰展示指标和趋势，点击进入业务详情；图表资源本地打包 |
| 项目、融资债务、速记及各部门台账 | Compose 分组表单、ViewModel/StateFlow、LazyColumn、Paging 3 | 处理多品种动态字段、关联对象选择、大量记录、分页筛选和宽表展示 |
| 本息计划、费用、担保抵扣、利率反算 | BigDecimal、LocalDate；后端 Decimal 与现有计算服务 | 避免金额精度和日期口径偏差；正式计算集中在后端，并对照 Web 行为补齐规则 |
| 基础资料、机构、账户与台账视图设置 | Compose 表单/选择器、Retrofit；DataStore 保存本机偏好 | 远程搜索与选择关联对象，提交稳定 ID；列设置和筛选语义复用后端，本机偏好单独保存 |
| 本地多轮对话、AI 辅助录入与续办 | Room、Android Keystore + AES-GCM、Compose 业务卡片；自有模型、现有 LangChain，必要时 LangGraph | 手机保存加密历史、摘要和草稿；自有服务器临时推理与调用业务工具，提交前展示确认内容 |
| 拍照、附件、OCR 识别及复核 | CameraX、系统文件选择器、Coil、PdfRenderer、Compose Canvas；服务器 OCR | 完成采集、上传、预览、识别及纠错，并在原文中高亮识别位置 |
| 自动填表、初始化导入、材料整理 | Compose 字段映射面板、WebViewAssetLoader + 本地 HTML/CSS；后端规则与 openpyxl | 展示复杂合并单元格，复核字段映射，复用服务器模板处理和文件生成 |
| 查询中心、统计报表、导出与打印 | Compose、ECharts；后端 openpyxl/python-docx；PDF 预览及 PrintDocumentAdapter | 查询和导出保持同一数据口径；原格式文件下载，打印所需 PDF 能力另行补齐 |
| 审批、协同、批量操作 | Compose 状态页面、Retrofit；后端权限、事务及版本/幂等机制 | 展示待办与处理结果，防止重复提交和多人修改互相覆盖；逐接口核实后端支持情况 |
| 上传、识别、导出等长任务与任务中心 | 前台协程轮询、WorkManager、服务端现有 Worker | 前台显示进度，后台安排可延迟工作；保存任务 ID，按接口能力提供重试、取消和恢复 |
| 系统参数、用户权限、AI 配置、LPR/节假日、备份恢复及审计 | Compose 管理表单/列表、Retrofit、后端管理接口 | 为有权限的用户提供完整管理入口，展示操作结果；耗时操作纳入任务中心 |

边界说明：允许自有服务器处理对话及业务附件，不要求离线办理正式业务。聊天正文和摘要不在服务器持久化、不发送第三方模型；现有后端聊天存储需要配套调整。Room 本身不提供数据库加密，需要单独实现敏感内容加密与账号隔离。

Hilt、按业务拆分 Gradle 模块等在复杂度增加后再引入；当前采用轻量手工组装。成本测算、AI 报告生成（定制）仍按现有业务方案标记为占位，不算已实现功能。

## 3. 建议的复盘顺序

1. **先看页面与路由**：[MainActivity](../app/src/main/java/com/citybond/mobile/MainActivity.kt) → [主题](../app/src/main/java/com/citybond/mobile/ui/Theme.kt) → [CityBondApp](../app/src/main/java/com/citybond/mobile/ui/CityBondApp.kt)。理解应用入口、组件和返回栈。
2. **再看状态与请求**：[ConnectionScreen](../app/src/main/java/com/citybond/mobile/ui/ConnectionScreen.kt) → [NetworkClient](../app/src/main/java/com/citybond/mobile/network/NetworkClient.kt)。理解点击如何变成请求，结果如何刷新页面。
3. **最后看验证方法**：[网络单测](../app/src/test/java/com/citybond/mobile/network/NetworkClientTest.kt)、[路由测试](../app/src/androidTest/java/com/citybond/mobile/NavigationTest.kt)，运行命令见 [README](../README.md)。

当前请求链路：`Compose 页面 → ViewModel / 协程 → Retrofit 接口与 JSON 解析 → OkHttp → 测试服务 /health`。接入正式业务后，服务端链路再连接 FastAPI、业务服务和数据库；当前尚未完成正式后端联调。

每完成一个小批次，将对应业务行更新为“已实现”，补上主要代码入口和验证结果即可；不需要为尚未开发的模块提前引入全部依赖。
